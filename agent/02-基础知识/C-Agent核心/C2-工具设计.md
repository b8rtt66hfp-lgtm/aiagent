# C2 · 工具设计

> 对应关卡：L4
> 面试权重：高。工具是 Agent 的"手"。**模型选错工具，90% 是工具设计的问题，不是模型笨。**

---

## 1. 一句话结论

**工具设计 = 给模型设计一个"人类新员工也能看懂"的接口。**
描述说清什么时候用、参数尽量少而严、返回精简、错误可行动、写操作要安全。做到这五点，工具调用准确率会有质的变化。

---

## 2. 概念

### 2.1 模型是怎么"选工具"的

模型看到的只有三样东西：**工具名、描述、参数的 JSON Schema**。
它没有你的代码，不知道函数体里发生了什么。选择过程本质是：读用户意图 → 匹配工具描述 → 生成参数。

推论：

- 描述写得含糊 → 选错
- 两个工具描述重叠 → 随机选
- 参数太多太自由 → 编造参数
- 工具超过 20 个 → 选择准确率明显下降

### 2.2 工具描述的写法

```python
# 差
def query(q: str) -> str:
    """查询"""

# 好
def search_orders(keyword: str, status: str = "all") -> str:
    """按关键词搜索订单。

    何时使用：用户询问"我的订单到哪了""有没有 XXX 的订单"等订单查询问题。
    何时不要用：用户要修改/取消订单时，请使用 update_order 工具。
    """
```

三段式：**做什么 / 何时用 / 何时不用**。第三段最容易被忽略，但它是区分相似工具的关键。

### 2.3 参数设计原则

| 原则 | 说明 |
| --- | --- |
| 少 | 能推导的参数不要让模型填（如 user_id 从会话里取） |
| 严 | 用 `Literal`/Enum 限制取值，用 `Field(ge/le)` 限制范围 |
| 有默认值 | 非关键参数给默认值，降低出错面 |
| 有描述 | 每个字段写格式和示例，例如 "日期 YYYY-MM-DD" |
| 不暴露内部标识 | 数据库主键、内部 ID 由服务端映射，不给模型 |

**安全原则**：`user_id`、`tenant_id` 这类身份参数必须从会话上下文注入，**绝不能让模型传**，否则就是越权漏洞。

### 2.4 粒度：一个工具做一件事

反例：`manage_order(action, order_id, amount, reason)`，一个工具包办查/改/退。模型很容易把 `action` 填错。

正确拆分：

- `get_order(order_id)`
- `cancel_order(order_id, reason)`
- `refund_order(order_id, amount)`

但也不能过度细分（`get_order_status`、`get_order_amount`、`get_order_eta` 分三个），否则模型要串行调三次。**按"用户意图"划分，而不是按数据库字段划分。**

### 2.5 返回值：给模型看，不是给程序看

```python
# 差：把整个 API 响应塞回去
return json.dumps(response)          # 3000 token

# 好：只留决策所需信息
return f"订单 ORD-001：已发货，预计明天送达，金额 199 元"
```

判断标准：**这个字段会影响模型下一步决策吗？** 不会就删。

### 2.6 错误的四种类型，四种返回

| 错误类型 | 返回给模型的话 | 意图 |
| --- | --- | --- |
| 参数错误 | "缺少必填参数 order_id，请向用户确认" | 让它补参数或反问用户 |
| 资源不存在 | "订单不存在，请让用户核对订单号" | 不要重试，换路径 |
| 系统错误（5xx/超时） | "订单系统暂时不可用，请稍后重试，不要连续调用" | 抑制重试风暴 |
| 权限不足 | "当前用户无权查看该订单" | 终止，不要绕路 |

**永远不要把 traceback 丢给模型**——它读不懂，还会浪费 token。

### 2.7 副作用与安全

1. **读写分离**：查询工具和写操作工具分开命名（`get_*` / `update_*`），便于做权限和确认。
2. **危险操作要确认**：退款、删除、发邮件，执行前需要人工确认（HITL）或二次校验。
3. **幂等**：写工具带幂等键，防重试重复执行。
4. **沙箱**：执行代码、访问文件系统的工具必须隔离运行。
5. **最小权限**：工具的凭证只授予必要范围。

### 2.8 工具多了怎么办

- 按领域分组，先路由再选工具（Router）
- 用 MCP 把工具拆成独立服务，按需挂载
- 动态工具集：根据当前会话场景只暴露相关工具

> MCP（Model Context Protocol）解决的正是"工具怎么标准化接入"：工具提供方实现一个 server，Agent 侧统一发现和调用。面试能说清这一句即可，不必背协议细节。

## 3. 最小可运行代码

### 3.1 用 Pydantic 定义工具 + 自动生成 schema

```python
from typing import Literal
from pydantic import BaseModel, Field


class RefundArgs(BaseModel):
    order_id: str = Field(description="订单号，形如 ORD-2026-0001")
    amount: float = Field(gt=0, description="退款金额，单位元")
    reason: Literal["质量问题", "七天无理由", "发错货"] = Field(description="退款原因")


class Tool:
    def __init__(self, name: str, description: str, args_model: type[BaseModel], func):
        self.name = name
        self.description = description
        self.args_model = args_model
        self.func = func

    def schema(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.args_model.model_json_schema(),
            },
        }

    def run(self, raw_args: dict) -> str:
        try:
            args = self.args_model.model_validate(raw_args)
        except Exception as e:
            return f"参数错误：{e.errors()[0]['msg']}。请修正后重试。"
        try:
            return str(self.func(**args.model_dump()))
        except Exception as e:
            return f"执行失败：{e}。请勿重复相同调用，可换一种方式。"
```

### 3.2 一个"设计得好"的完整工具

```python
def refund_order(order_id: str, amount: float, reason: str) -> str:
    """为用户办理退款。

    何时使用：用户明确要求退款，且订单已支付时。
    何时不要用：订单未支付、已退款、超过 30 天时不要使用，应向用户说明。
    注意：金额不得超过订单实付金额；本操作有副作用。
    """
    if amount <= 0:
        return "退款金额必须大于 0，请与用户确认。"
    # 真实实现省略
    return f"退款成功：订单 {order_id}，金额 {amount} 元，原因「{reason}」，3 个工作日内到账。"


refund_tool = Tool(
    name="refund_order",
    description=refund_order.__doc__ or "",
    args_model=RefundArgs,
    func=refund_order,
)
```

## 4. 常见坑

1. **描述里只有功能名**：模型不知道边界，相似工具之间乱选。
2. **一个工具塞多种能力**：`action` 参数本质是让模型做二级路由，错误率翻倍。
3. **参数里带 `user_id`**：越权风险，身份必须服务端注入。
4. **返回整段 JSON/HTML**：token 浪费 + 干扰决策。
5. **错误直接抛异常**：循环中断，用户看到 500。
6. **工具名相似**：`search` / `query` / `find` 三个并存，模型必然混淆。
7. **无超时**：一个慢工具卡住整个 Agent。
8. **写操作可被自由重试**：重复退款、重复发信。
9. **工具数量爆炸**：30 个工具全量暴露，选择准确率暴跌，应做分组或路由。

## 6. 参考答案与自测标准

### 练习 1 答案

```
按订单号或关键词查询订单状态与物流信息。
何时使用：用户询问订单进度、是否发货、预计到达时间。
何时不要用：用户要取消/修改/退款时，请使用对应工具，不要用本工具代替。
```

**自测标准**：包含"做什么 + 何时用 + 何时不用"。

---

### 练习 2 答案

- `get_user(user_id)`：只读，仅本人或管理员
- `update_user(user_id, fields)`：写，仅本人，字段白名单
- `delete_user(user_id, confirm_token)`：写，仅管理员，需要二次确认

拆分后每个工具的描述边界清晰，权限也能分别控制。

**自测标准**：拆分依据是"权限和副作用不同"，不是"代码行数"。

---

### 练习 3 答案

1. 格式错：`"收件人邮箱格式不正确，请向用户确认后重试，不要重复发送。"`
2. 服务 500：`"邮件服务暂时不可用，已记录，请告知用户稍后再试。"`
3. 配额用尽：`"今日邮件配额已用尽，请改为其他通知方式或告知用户明天再试。"`

**自测标准**：每条都给了模型"下一步做什么"，而不是只说"失败了"。

---

### 练习 4 答案

1. 工具描述没提"订单"，模型只能选到一个相关工具 → 补描述
2. 没有订单查询工具 → 新增 `get_orders`
3. 工具太多，模型选择困难 → 分组/路由，只暴露相关工具
4. 用户提问里"订单"指的可能是购物车 → 增加澄清逻辑
5. 模型没有工具调用能力或参数格式错 → 检查 model 与 schema
6. 系统提示没要求先查工具 → 加强指令

**自测标准**：能从"描述、工具集、提示词、模型能力"四个层面排查。

---

### 练习 5 答案

- 需要显式 `confirm_token`（由用户二次确认后生成）
- 仅管理员权限，工具内部校验
- 软删除 + 可恢复
- 记录审计日志
- 限流，防批量误删

**自测标准**：能说出"权限在代码里校验，不能只靠提示词约束"。

## 7. 面试问法

| 面试官可能这么问 | 你要答到的点 |
| --- | --- |
| 怎么让模型正确调用工具 | 描述三段式、参数少而严、工具单一职责、结果裁剪 |
| 模型总选错工具怎么排查 | 描述是否重叠、工具是否过多、参数是否复杂、提示词是否引导 |
| 工具报错怎么返回 | 四类错误四类话术，转成可行动信息，不抛 traceback |
| 工具返回值要不要全给模型 | 不要，按"是否影响下一步决策"裁剪 |
| 危险操作怎么防 | 权限校验、二次确认、幂等、审计、限流、沙箱 |
| 工具太多怎么办 | 分组路由、动态暴露、MCP 拆分服务 |
