# C3 · 记忆与上下文管理

> 对应关卡：L4 ~ L5
> 面试权重：高。必问题："多轮对话上下文怎么管？超了怎么办？"

---

## 1. 一句话结论

**上下文窗口是预算，不是仓库。** 记忆管理的本质是回答一个问题：**这一轮调用，哪些信息必须进 prompt，哪些必须扔掉或压缩？**
不做管理的 Agent，跑到第 10 轮就会又贵又慢又失忆。

---

## 2. 概念

### 2.1 两类记忆

| 类型 | 存在哪 | 存什么 | 生命周期 |
| --- | --- | --- | --- |
| 短期记忆 | 本次请求的 `messages` 列表 | 最近几轮对话、工具调用记录 | 单次会话 |
| 长期记忆 | 外部存储（数据库/向量库） | 用户偏好、历史结论、知识 | 跨会话 |

短期记忆决定"这一轮能不能接上话"，长期记忆决定"下次还认不认识你"。

### 2.2 上下文的成本结构

一次调用的 token = 系统提示 + 历史消息 + 检索内容 + 工具结果 + 本轮输入 + 输出预算。

**历史是增长最快的部分**：每轮都全量回传，第 10 轮的成本是第一轮的 10 倍。

### 2.3 四种窗口管理策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 全量 | 全都带上 | 信息完整 | 很快超限、贵 |
| 滑动窗口 | 只带最近 N 轮 | 简单、成本可控 | 早期信息丢失 |
| 摘要压缩 | 旧对话压成摘要 | 保留主线 | 细节丢失、摘要本身有成本 |
| 分层 | 系统规则 + 摘要 + 最近 N 轮 + 按需检索 | 兼顾成本与信息 | 实现复杂 |

生产上通常是**分层**：底噪声内容（寒暄、工具原始输出）直接丢，重要结论进摘要，最近几轮保留原文。

### 2.4 什么时候做压缩

不要等超限才压缩。推荐按 token 预算触发：

```
if count_tokens(messages) > 0.7 * 可用窗口:
    压缩最旧的若干轮 → 一条摘要
```

保留的结构：

```
[system]
[历史摘要]
[最近 6 轮原文]
[本轮用户输入]
```

### 2.5 什么该进长期记忆

值得记：

- 用户偏好（"我只要中文回答""预算不超过 500"）
- 已完成的关键结论（"已确认订单 ORD-001 退款"）
- 未完成事项（下次接着做）
- 稳定事实（所在城市、角色）

不值得记：

- 寒暄、重复确认
- 工具返回的原始 JSON
- 模型的长篇推理过程

**判断标准：这条信息下次会话还用得上吗？**

### 2.6 记忆的写入、更新与遗忘

- **写入**：会话结束或触发关键事件时抽取，而不是每轮都写
- **更新**：新信息覆盖旧信息，保留时间戳；冲突时以最新为准
- **遗忘**：TTL 过期、按重要度淘汰、用户主动清除
- **隔离**：所有读写必须带 `user_id` / `session_id` 过滤，否则会串话

### 2.7 摘要的陷阱

摘要会**二次失真**：摘摘要的摘要，几轮之后关键数字就没了。
对策：摘要只压"过程性内容"，**关键实体（订单号、金额、日期）单独用结构化字段存**，不依赖摘要。

## 3. 最小可运行代码

### 3.1 滑动窗口 + 摘要压缩

```python
from openai import OpenAI

client = OpenAI()
MAX_CHARS = 6000          # 简化：用字符数近似 token


def estimate(messages: list[dict]) -> int:
    return sum(len(str(m.get("content", ""))) for m in messages)


def summarize(messages: list[dict]) -> str:
    text = "\n".join(f"{m['role']}: {m.get('content', '')}" for m in messages)
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        temperature=0,
        messages=[{
            "role": "user",
            "content": "把以下对话压缩成不超过 150 字的摘要，保留数字、单号、结论和未完成事项：\n" + text,
        }],
    )
    return resp.choices[0].message.content


def build_context(system: str, history: list[dict], question: str, keep_recent: int = 6) -> list[dict]:
    messages = [{"role": "system", "content": system}]
    if estimate(history + [{"role": "user", "content": question}]) > MAX_CHARS:
        old, history = history[:-keep_recent], history[-keep_recent:]
        if old:
            messages.append({"role": "system", "content": "历史摘要：" + summarize(old)})
    messages.extend(history)
    messages.append({"role": "user", "content": question})
    return messages
```

### 3.2 长期记忆的最小实现

```python
import sqlite3
import json

conn = sqlite3.connect("memory.db")
conn.execute("""
CREATE TABLE IF NOT EXISTS memory (
    user_id TEXT, key TEXT, value TEXT, updated_at TEXT,
    PRIMARY KEY (user_id, key)
)
""")


def remember(user_id: str, key: str, value: str):
    conn.execute(
        "INSERT OR REPLACE INTO memory VALUES (?, ?, ?, datetime('now'))",
        (user_id, key, json.dumps(value, ensure_ascii=False)),
    )
    conn.commit()


def recall(user_id: str, key: str) -> str | None:
    row = conn.execute(
        "SELECT value FROM memory WHERE user_id=? AND key=?", (user_id, key)
    ).fetchone()
    return json.loads(row[0]) if row else None
```

关键点：**每条记忆都带 `user_id`**，查询时强制过滤。

### 3.3 工具结果的裁剪

```python
def trim_tool_result(text: str, limit: int = 1500) -> str:
    if len(text) <= limit:
        return text
    return text[:limit] + "\n...[内容过长已截断，如需更多请缩小查询范围]"
```

截断时**告诉模型被截断了**，否则它会把残缺内容当完整事实。

## 4. 常见坑

1. **无脑全量回传**：第 10 轮成本和延迟都不可接受。
2. **摘要丢关键数字**：订单号、金额必须结构化保存。
3. **跨用户串记忆**：查询忘记加 `user_id`，A 用户看到 B 的偏好。
4. **把工具原始输出写进长期记忆**：噪声大、很快过时。
5. **摘要递归压缩**：摘摘要越来越短，最后只剩"用户咨询了订单问题"。
6. **不计算 token**：凭感觉判断"应该没超"。
7. **截断不提示**：模型基于残缺信息给出错误结论。
8. **历史里保留失败的中间步骤**：模型会被自己的错误带偏。

## 5. 练习

### 练习 1（入门）· 估算

一个 20 轮的客服对话，每轮约 200 字，system 500 字。全量回传每轮消耗多少字？第 20 轮大约是第 1 轮的几倍？

### 练习 2（核心）· 设计压缩策略

写出你的 `build_context` 分层结构，说明每层放什么、触发压缩的条件是什么。

### 练习 3（核心）· 选入长期记忆

以下信息哪些值得写入长期记忆：A. "我下周要出差去上海"；B. "你好"；C. "我的会员等级是金卡"；D. 工具返回的完整商品列表；E. "上次那个方案先不做了"。

### 练习 4（进阶）· 记忆冲突

用户先说"我喜欢简洁回答"，后来说"详细一点"。你的系统怎么处理？表结构怎么设计？

### 练习 5（进阶）· 工具结果失控

## 6. 参考答案与自测标准

### 练习 1 答案

每轮输入约 200 字，第 20 轮累计约 19 × 200 + 500 + 200 ≈ 4500 字。约为第 1 轮的 9 倍（第 1 轮约 700 字）。
真实 token 还要算工具返回和输出，通常比字符估算更夸张。

**自测标准**：能意识到"成本随轮次线性增长甚至更快"。

---

### 练习 2 答案

```
[system]       角色、规则、输出格式        —— 常驻
[long_summary] 历史摘要（触发后生成）      —— 超过 70% 窗口时压缩最旧轮次
[recent N]     最近 6 轮原文               —— 常驻
[retrieved]    按需检索的知识片段          —— 与本轮问题相关才加
[user]         本轮输入                    —— 常驻
```

触发条件用 token 计数，不用轮数。

**自测标准**：能说出"系统提示和最近轮次不参与压缩"。

---

### 练习 3 答案

值得：C（稳定偏好）、E（未完成事项，需带时间上下文）
不值得：B（寒暄）、D（噪声且易过时）
A 可记但要有 TTL（一周后失效）

**自测标准**：用"下次是否还用得上 + 是否会过期"两个维度判断。

---

### 练习 4 答案

以最新为准，但保留历史：

```sql
CREATE TABLE memory (
  user_id TEXT, key TEXT, value TEXT,
  updated_at TEXT, version INT,
  PRIMARY KEY (user_id, key, version)
);
```

写入新值时 `version + 1`，查询取最大 version；需要审计时能回看历史。

**自测标准**：能说出"冲突不是删除，而是版本覆盖 + 时间戳"。

---

### 练习 5 答案

1. 裁剪：只取前 1500 字，并注明已截断
2. 让工具直接返回摘要字段，而不是全文
3. 分页/分段读取，模型按需再查
4. 检索后先做摘要再入上下文
5. 降低 top_k 或提高相关性阈值

**自测标准**：优先在"工具侧"解决，而不是在"上下文侧"硬塞。

## 7. 面试问法

| 面试官可能这么问 | 你要答到的点 |
| --- | --- |
| 多轮上下文怎么管 | 分层：系统 + 摘要 + 最近 N 轮 + 按需检索；按 token 触发压缩 |
| 超窗口怎么办 | 滑动窗口、摘要、裁剪工具结果、RAG 替代全量 |
| 长期记忆怎么存 | 结构化 KV（偏好/事实）+ 向量库（情景），带 user_id 隔离、TTL |
| 摘要会不会丢信息 | 会，所以关键实体结构化保存，摘要只压过程 |
| 怎么防串话 | 所有读写带 user_id/session_id 强制过滤 |
| 记忆什么时候写 | 关键事件或会话结束抽取，不要每轮写 |
